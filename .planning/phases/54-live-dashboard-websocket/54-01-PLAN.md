# Phase 54: Live Dashboard WebSocket

## Goal

Wire the Next.js dashboard to the API gateway's existing WebSocket for real-time state updates, replacing the dashboard's local file-watching SSE mechanism.

## Current Architecture

```
GYWD Files (.planning/, ~/.gywd/)
  ├─→ [API Gateway :3945] → REST + WS broadcast (UNUSED by dashboard)
  └─→ [Dashboard :3000]   → Direct fs.watch + SSE → Browser
```

## Target Architecture

```
GYWD Files (.planning/, ~/.gywd/)
  └─→ [API Gateway :3945] → REST + WS broadcast
                                    ↓
       [Dashboard :3000] ←── WS client ←── useWebSocket hook
                                    ↓
                              Browser Client
```

## Tasks

### Task 1: Create `useWebSocket` React hook
**File:** `dashboard/src/lib/hooks/useWebSocket.ts`

Create a WebSocket client hook that:
- Connects to `ws://localhost:3945/ws` (configurable via env `NEXT_PUBLIC_GYWD_API_URL`)
- Parses incoming `{ event, data, timestamp }` messages from the API gateway
- Maps events: `state_changed`, `patterns_updated`, `data_updated`, `heartbeat`
- Auto-reconnects on disconnect (exponential backoff: 1s, 2s, 4s, 8s, max 30s)
- Exposes: `{ connected, lastEvent, error, reconnecting }`
- Same interface as `useSSE` so components can swap easily

### Task 2: Create WebSocket API client
**File:** `dashboard/src/lib/ws-client.ts`

Server-side WebSocket client for Next.js API routes:
- Singleton `WsClient` class that connects to the API gateway WS
- Maintains connection from dashboard server process (not browser)
- Buffers recent events (last 50) for late-joining API route requests
- Exposes `onEvent(callback)`, `getLatestState()`, `isConnected()`
- Used by dashboard API routes to proxy WS data to browser SSE (transition period)

### Task 3: Update dashboard API routes to use API gateway
**Files:** `dashboard/src/app/api/status/route.ts`, `dashboard/src/app/api/patterns/route.ts`, `dashboard/src/app/api/memory/route.ts`, `dashboard/src/app/api/planning/route.ts`

Replace direct filesystem reads with API gateway REST calls:
- `GET /api/status` → fetch from `http://localhost:3945/api/v1/status`
- `GET /api/patterns` → fetch from `http://localhost:3945/api/v1/patterns`
- `GET /api/memory` → fetch from `http://localhost:3945/api/v1/memory`
- `GET /api/planning` → fetch from `http://localhost:3945/api/v1/planning`
- Pass API key from env `GYWD_API_KEY` (or `GYWD_API_AUTH=disabled` for dev)
- Add error handling: if gateway is down, fall back to direct fs reads via gywd-bridge

### Task 4: Update dashboard SSE stream to proxy gateway WS
**File:** `dashboard/src/app/api/stream/route.ts`

Replace file-watching SSE with WS proxy:
- Connect to `ws://localhost:3945/ws` via the `ws-client.ts` singleton
- Forward all WS events as SSE events to browser (same event names)
- Maintain SSE heartbeat for browser connection keepalive
- Fallback: if WS connection fails, fall back to old file-watching SSE

### Task 5: Update dashboard components to use `useWebSocket`
**Files:** Components that currently import `useSSE`

- Find all `useSSE` imports and replace with `useWebSocket`
- The hook interface is the same, so component code should need minimal changes
- Add a connection status indicator in the dashboard header

### Task 6: Add gateway URL configuration
**Files:** `dashboard/.env.local.example`, `dashboard/src/lib/config.ts`

- `NEXT_PUBLIC_GYWD_API_URL=http://localhost:3945` (browser-side, for WS hook)
- `GYWD_API_URL=http://localhost:3945` (server-side, for API route proxying)
- `GYWD_API_KEY=` (optional, for authenticated gateway)
- Create a `getApiConfig()` helper

### Task 7: Write tests
**Files:** `dashboard/tests/ws-client.test.ts`, `dashboard/tests/useWebSocket.test.ts`

- Test WS client connection, reconnection, event buffering
- Test useWebSocket hook states (connected, disconnected, reconnecting)
- Test API route proxy (mock fetch to gateway)
- Test fallback behavior when gateway is unavailable

## Key Decisions

- **Dual-mode operation:** Dashboard works with OR without the API gateway running (falls back to direct fs reads)
- **Keep SSE to browser:** Browser still gets SSE from dashboard — the WS connection is dashboard-server ↔ API gateway, not browser ↔ API gateway directly. This avoids CORS/auth complexity in the browser.
- **Same event shape:** WS events from gateway already match SSE events (`state_changed`, `patterns_updated`, etc.) — no translation needed

## Dependencies

- API gateway must be running on port 3945 for live features
- Dashboard works standalone (degraded — no real-time) without gateway

## Success Criteria

- [ ] Dashboard connects to API gateway WebSocket on startup
- [ ] State changes in `.planning/STATE.md` appear in dashboard within 500ms
- [ ] Pattern changes appear in dashboard within 500ms  
- [ ] Dashboard still works if API gateway is not running (fallback mode)
- [ ] Auto-reconnect works when gateway restarts
- [ ] All existing dashboard tests still pass
- [ ] New WS tests pass
